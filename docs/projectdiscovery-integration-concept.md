# Концепция расширения интеграции с инструментами ProjectDiscovery

> Документ на русском языке. Russian-language design document.

Проектный документ / Архитектурная концепция. Описывает возможности, сценарии и архитектурный дизайн интеграции инструментов экосистемы **ProjectDiscovery** в сканирующий конвейер и платформу управления поверхностью атаки (EASM) **Shapoclyack**.

---

## 1. Контекст и текущее состояние

В текущей версии Shapoclyack уже интегрированы три инструмента ProjectDiscovery:

| Инструмент | Версия | Лицензия | Назначение в Shapoclyack | Файлы реализации |
|---|---|---|---|---|
| **Naabu** | `2.6.1` | MIT | Быстрый SYN/CONNECT скан портов, probe ladder (alive detection) | [`scanner/pipeline/ports.py`](../scanner/pipeline/ports.py), [`scanner/pipeline/probe_ladder.py`](../scanner/pipeline/probe_ladder.py) |
| **Nuclei** | `3.11.1` | MIT | Шаблонное сканирование уязвимостей и мисконфигураций веб-сервисов | [`scanner/pipeline/nuclei_scan.py`](../scanner/pipeline/nuclei_scan.py), [`Dockerfile`](../Dockerfile) (стадия `go-tools`, шаблоны `NUCLEI_TEMPLATES_REF=v9.9.4`) |
| **DNSx** | `1.2.3` | MIT | Резолвинг DNS, PTR lookup, поиск dangling CNAME / takeover, DNS/почтовая гигиена | [`scanner/pipeline/dnsx.py`](../scanner/pipeline/dnsx.py) (общая обёртка), [`scanner/pipeline/domain_monitor.py`](../scanner/pipeline/domain_monitor.py), [`scanner/pipeline/resolve.py`](../scanner/pipeline/resolve.py), [`scanner/pipeline/dns_hygiene.py`](../scanner/pipeline/dns_hygiene.py), [`scanner/pipeline/mail_posture.py`](../scanner/pipeline/mail_posture.py) |

Все три инструмента **собираются из исходников** на стадии `go-tools` в [`Dockerfile`](../Dockerfile) и [`Dockerfile.allinone`](../Dockerfile.allinone) (Go 1.26, `GO_SECURITY_PINS` поверх их `go.mod`); SHA-256-пины релизных архивов ушли вместе с самими архивами, модули проверяются через `GOSUMDB`. Бинарники запускаются в непривилегированном режиме с минимально необходимыми Linux Capabilities (`cap_net_raw,cap_net_admin` для Naabu, Pulse и, если установлен, Nmap).

## 2. Лицензионная чистота и безопасность

* **Лицензирование:** Все рассматриваемые CLI-инструменты ProjectDiscovery распространяются под пермиссивной лицензией **MIT License**. Они полностью совместимы с коммерческим и открытым использованием, не накладывают copyleft-ограничений (в отличие от GPLv3 у Nmap) и безопасны для включения в базовые образы контейнеров.
* **Безопасность поставок (Supply Chain):** Бинарные файлы пинятся по фиксированным тегам версий (`ARG`) и компилируются из исходников с фиксированным Go toolchain и проверкой модулей через `GOSUMDB` (так уже сделано для `naabu`, `nuclei`, `dnsx`), после чего проверяются статическими анализаторами (Trivy).

## 3. Обзор компонентов для расширения

Ни один из перечисленных ниже инструментов в конвейере пока **не реализован**; это кандидаты.

| Утилита | Лицензия | Роль в конвейере безопасности |
|---|---|---|
| **`httpx`** | MIT | Быстрый HTTP-пробинг, определение CMS/WAF/CDN, хэширование фавиконов (MMH3), сбор тайтлов и статусов. |
| **`subfinder`** | MIT | Пассивный поиск поддоменов без прямого шума по 40+ открытым и API-источникам (CT-логи, Shodan, Censys и др.). |
| **`tlsx`** | MIT | Быстрый сбор TLS/SSL-сертификатов, SAN, дат экспирации, слабых шифров и JARM/JA3S отпечатков. |
| **`katana`** | MIT | Современный краулер/паук веб-приложений (включая Headless Chromium для SPA) для извлечения эндпоинтов и параметров. |
| **`asnmap`** | MIT | Преобразование ASN/имени организации/домена в CIDR-блоки подсетей. |
| **`alterx`** | MIT | Быстрая мутация и генерация перестановок субдоменов по шаблонам. |
| **`interactsh`** | MIT | Out-Of-Band (OOB) сервер/клиент для подтверждения "слепых" уязвимостей (Blind SSRF, Blind RCE, XXE, Log4Shell). |

## 4. Сценарии использования и архитектурный дизайн

### Сценарий 1: Автоматический скоупинг и расширение периметра (Asset Reconnaissance)
* **Проблема:** Пользователь задает корневой домен или имя компании, но дочерняя инфраструктура распределена по сотням поддоменов и диапазонов.
* **Цепочка:** `asnmap` ➔ `subfinder` ➔ `alterx` ➔ `dnsx`
* **Процесс:**
  1. `asnmap` по названию компании/ASN находит все закрепленные IP-диапазоны.
  2. `subfinder` пассивно извлекает все зарегистрированные поддомены из CT-логов и внешних агрегаторов.
  3. `alterx` генерирует возможные мутации (`stage-api`, `dev-admin`, `corp-vpn`).
  4. `dnsx` валидирует существование записей и отсекает мертвые хосты.
* **Результат:** Формирование точного инвентаря целей для передачи в стадию обнаружения хостов.

---

### Сценарий 2: Комплексный Web Probing и Fingerprinting сервисов
* **Проблема:** `naabu` сообщает только `host:port`, требуются тяжелые Nmap-скрипты или кастомные Python-пробы для понимания веб-стека.
* **Цепочка:** `naabu` (open ports) ➔ `httpx` (web metadata)
* **Процесс:**
  1. `httpx` параллельно подключается ко всем открытым HTTP/HTTPS портам.
  2. Извлекает технологии через встроенный движок Wappalyzer, статус-коды, редиректы, CDN-признаки.
  3. Вычисляет Favicon MMH3 hash (мгновенный поиск панелей Spring Boot, Jenkins, Keycloak, Swagger UI).
  4. Схлопывает дублирующиеся страницы-заглушки по Response Body Hash.
* **Результат:** Обогащение сущности сервиса в БД Shapoclyack структурированными метаданными о веб-приложении.

---

### Сценарий 3: Глубокий DAST-аудит веб-приложений (Crawling + Nuclei)
* **Проблема:** `nuclei` по умолчанию тестирует только корень URL, не покрывая внутренние маршруты SPA и REST API.
* **Цепочка:** `httpx` ➔ `katana` ➔ `nuclei`
* **Процесс:**
  1. По обнаруженным живым веб-приложениям запускается `katana` с ограничением по глубине и времени.
  2. `katana` парсит JS-бандлы, находит скрытые API-эндпоинты, параметры запросов и роуты.
  3. Сформированный список эндпоинтов передается в `nuclei` для адресной проверки параметров (IDOR, SQLi, XSS, открытые spec-файлы).
* **Результат:** Переход от простого поверхностного сканера к полноценному DAST веб-приложений.

---

### Сценарий 4: Детект слепых уязвимостей (Out-of-Band / OOB Testing)
* **Проблема:** Уязвимости вроде Blind SSRF, Blind RCE, Log4Shell не возвращают пейлоад в ответе HTTP, что приводит к ложноотрицательным результатам.
* **Цепочка:** `nuclei` + `interactsh-client` ➔ `interactsh-server`
* **Процесс:**
  1. В инфраструктуре разворачивается защищенный приватный сервер `interactsh`.
  2. `nuclei` при сканировании подставляет уникальные DNS/HTTP callback-домены в нагрузках.
  3. При обращении уязвимого хоста к `interactsh` фиксируется факт эксплуатации с точностью 100%.
* **Результат:** Достоверный детект критических уязвимостей периметра без ложных срабатываний.

---

### Сценарий 5: Аудит TLS-постуры и криптографической гигиены
* **Проблема:** Необходимость контроля истечения сертификатов, использования устаревших протоколов (TLS 1.0/1.1) и выявления аномалий.
* **Инструмент:** `tlsx`
* **Процесс:**
  1. Сканирование всех TLS-сервисов, выгрузка цепочек сертификатов и Subject Alternative Names (SAN).
  2. Автоматическое вычисление JARM/JA3S отпечатков (группировка идентично сконфигурированных серверов).
  3. Генерация событий и алертов на сертификаты с истекающим сроком действия (< 14 / < 30 дней) или самоподписанные сертификаты на внешнем контуре.
* **Результат:** Формирование раздела соответствия требованиям безопасности (PCI-DSS / ISO 27001) в отчетах Shapoclyack.

---

### Сценарий 6: Уведомления и интеграция с SOC
* **Проблема:** Операторам безопасности требуется оперативное оповещение о появлении уязвимостей Critical/High без ожидания сводного отчета.
* **Инструмент:** `notify`
* **Процесс:**
  1. При завершении скана или обнаружении находок заданного уровня критичности данные передаются в `notify`.
  2. `notify` отправляет форматированные сообщения в сконфигурированные каналы (Telegram, Slack, Discord, PagerDuty, Webhook).
* **Результат:** Минимальное время реакции (MTTR) дежурной смены на новые критические риски.

## 5. Общая схема конвейера (Pipeline Flow)

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Скоупинг и внешняя разведка                              │
│    asnmap  ──►  subfinder  ──►  alterx  ──►  dnsx           │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Обнаружение хостов и сканирование портов                 │
│    probe_ladder (ICMP / TCP)  ──►  naabu (SYN/CONNECT)      │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Фингерпринтинг и проверка сервисов                       │
│    httpx (Web/WAF/CDN)  +  tlsx (TLS hygiene/JARM)          │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Аудит уязвимостей (DAST & Vuln Engine)                   │
│    katana (Crawling/Endpoints) ──► nuclei + interactsh (OOB)│
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. Доставка результатов и алертинг                          │
│    Shapoclyack Risk Engine ──► notify / PDF / DefectDojo    │
└─────────────────────────────────────────────────────────────┘
```

## 6. Рекомендуемые этапы реализации

1. **Этап 1: Интеграция `httpx`** — дополнение / ускорение модуля `scanner/pipeline/fingerprint.py`, сбор favicon hash и точное определение веб-стека. (Сегодня fingerprint использует Python-библиотеку `httpx`, а не CLI ProjectDiscovery — это разные вещи.)
2. **Этап 2: Интеграция `subfinder` и `asnmap`** — расширение скоупинга в модуле организации [`docs/org-profile-module.ru.md`](org-profile-module.ru.md).
3. **Этап 3: Подключение `interactsh` к `nuclei`** — включение безопасного OOB-тестирования в `scanner/pipeline/nuclei_scan.py`.
4. **Этап 4: Интеграция `katana`** — опциональный режим глубокого DAST-сканирования веб-ресурсов.
