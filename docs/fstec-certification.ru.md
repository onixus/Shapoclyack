# План подготовки Shapoclyack к сертификации ФСТЭК России

> Статус: рабочий инженерный baseline на 2026-09-22. Документ не подтверждает наличие сертификата и не заменяет решение органа по сертификации или испытательной лаборатории.

## 1. Цель

Подготовить отдельную воспроизводимую конфигурацию **Shapoclyack Certified** к оценке соответствия требованиям ФСТЭК России.

Рабочая цель программы — проектирование под **4-й уровень доверия (УД4)** по приказу ФСТЭК России от 02.06.2020 № 76. Окончательный уровень доверия, назначение средства, состав сертифицируемой конфигурации и применимые специальные требования фиксируются только после согласования с органом по сертификации и испытательной лабораторией.

Важно различать:

- compliance mapping в отчетах Shapoclyack;
- применение Shapoclyack как средства в защищаемой системе;
- сертификацию самого Shapoclyack как средства защиты информации.

Наличие в продукте каталога мер ФСТЭК не является сертификацией продукта.

## 2. Нормативный baseline

Для планирования используются:

- приказ ФСТЭК России от 03.04.2018 № 55 «Об утверждении Положения о системе сертификации средств защиты информации»;
- приказ ФСТЭК России от 20.01.2026 № 9, изменивший порядок сертификации и состав представляемых материалов;
- приказ ФСТЭК России от 02.06.2020 № 76 «Об утверждении Требований по безопасности информации, устанавливающих уровни доверия…» с действующими изменениями;
- применимые профильные требования ФСТЭК к заявляемому типу средства после фиксации назначения и класса.

С 2026 года в подготовке заявки и испытательных материалов необходимо отдельно учитывать сведения о заимствованных компонентах и контейнерных образах, если они входят в состав средства.

## 3. Предлагаемая граница объекта оценки

Первый проход сертификации должен минимизировать trusted computing base. Предлагаемый объект:

```text
Shapoclyack Certified
├── API / control plane
├── RBAC / tenant isolation
├── scan orchestration
├── certified scanner execution profile
├── evidence / finding lifecycle
├── audit subsystem
├── Web UI administrative functions
└── required storage / messaging adapters
```

Отдельно классифицируются:

- PostgreSQL;
- NATS JetStream;
- ClickHouse;
- Pulse;
- ProjectDiscovery/Nuclei;
- базовые контейнерные образы;
- внешние threat-intelligence feeds;
- Lariska;
- Jira, ServiceNow, DefectDojo и иные внешние интеграции.

Для каждого компонента должно быть принято одно решение: **входит в объект оценки**, **является средой функционирования**, либо **является внешней интеграцией**.

Опциональные интеграции не должны автоматически расширять сертифицируемую границу.

## 4. Основные security invariants

Следующие свойства должны быть выражены в модели безопасности и иметь трассировку до тестов:

1. tenant не получает доступ к данным другого tenant;
2. сканирование выполняется только для явно разрешенного scope;
3. privileged operations доступны только авторизованным ролям;
4. переходы finding/remediation lifecycle выполняются только допустимыми субъектами и состояниями;
5. evidence и audit trail имеют определенную семантику целостности и происхождения;
6. scanner/sensor не может получить задания другого tenant;
7. отказ внешнего feed или аналитического хранилища не должен открывать обход авторизации;
8. обновление программных компонентов выполняется только из доверенного и проверяемого источника.

## 5. Сертификационный release train

Сертифицируемая конфигурация не должна собираться непосредственно из постоянно меняющегося `main`.

Предлагаемая схема:

```text
main
  └── release/*
       └── certified/<version>
```

Для `certified/*` обязательны:

- immutable dependency lock;
- фиксированные container digests;
- SBOM;
- provenance сборки;
- подпись релизных артефактов;
- архив исходного кода;
- архив build environment;
- идентификатор комплекта документации;
- traceability matrix;
- полный протокол CI/acceptance tests.

Любое изменение certified baseline проходит impact analysis.

## 6. Критические gap'ы

### 6.1 Transport trust для сенсоров и NATS

Для сертификационной конфигурации должны быть формально определены:

- TLS profile;
- взаимная аутентификация, если она требуется выбранной архитектурой;
- service identity;
- выпуск, ротация и отзыв credentials;
- поведение при истечении сертификата;
- fail-closed semantics.

Roadmap-функции не должны описываться как реализованные свойства certified build.

### 6.2 Supply chain

Необходимо поддерживать полный перечень:

- Python dependencies;
- npm dependencies;
- Rust/Go binaries;
- системные пакеты;
- container base images;
- scanner/templates;
- data feeds, если их содержимое влияет на функции безопасности.

Для каждой зависимости фиксируются версия, источник, лицензия, hash/digest, роль и политика обновления.

### 6.3 Security testing

Нужна трассировка:

```text
требование
  → функция безопасности
    → интерфейс
      → подсистема
        → модуль
          → test case
            → результат
```

Для УД4 проект должен исходить из полного покрытия заявленных функций безопасности испытаниями на соответствующем уровне детализации, а не из общей метрики line coverage.

### 6.4 Vulnerability response

Должны быть формализованы:

- источник сведений об уязвимостях;
- triage;
- impact analysis;
- исправление;
- regression testing;
- выпуск security update;
- уведомление потребителей;
- документирование компенсирующих мер.

## 7. Рабочий план

| Этап | Содержание | Результат | Оценка |
|---|---|---|---:|
| S0 | Выбор органа по сертификации/ИЛ, фиксация назначения | согласованный объект оценки | 2–3 нед. |
| S1 | Gap analysis к УД4 | матрица требований и backlog | 3–4 нед. |
| S2 | Freeze certified architecture | TCB, trust boundaries, interfaces | 3–5 нед. |
| S3 | Secure SDLC и управление конфигурацией | воспроизводимый процесс | 4–8 нед. |
| S4 | Product hardening | закрытые технические gap'ы | 6–10 нед. |
| S5 | Модель безопасности и проектная документация | комплект design evidence | 6–10 нед. |
| S6 | Эксплуатационная документация | формуляр и руководства | 3–5 нед. |
| S7 | Acceptance/traceability | доказательная тестовая база | 4–6 нед. |
| S8 | Внутренний предсертификационный аудит | закрытый blocker backlog | 2–4 нед. |
| S9 | Заявка и передача образца | formal certification start | зависит от ОС/ИЛ |
| S10 | Сертификационные испытания | протоколы и устранение замечаний | зависит от ОС/ИЛ |
| S11 | Сопровождение сертификата | controlled certified releases | постоянно |

Внутренний engineering track до передачи в ИЛ следует планировать как многомесячную программу. Срок внешней процедуры отдельно определяется органом по сертификации и испытательной лабораторией.

- vulnerability-response policy.

## 9. Definition of Ready для передачи в испытательную лабораторию

Shapoclyack не считается готовым только потому, что functional tests зеленые.

Готовность означает одновременно:

- объект оценки согласован;
- certified version frozen;
- нет demo/test authentication paths в сертифицируемой конфигурации;
- все security invariants проверяются;
- dependency/container inventory полный;
- сборка воспроизводима;
- release artifacts подписываются и идентифицируются;
- все требования имеют traceability;
- эксплуатационная документация соответствует фактическому поведению;
- нет известных blocker/critical несоответствий;
- процедура security-update протестирована.
