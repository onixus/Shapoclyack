# Наблюдение за брендом

Как оператор заводит профиль похожих имён, дожидается суточной пересборки и
получает только смену состояния. Имена из профиля **не сканируются** и не
попадают в область сканирования. Квоты — фиксированные значения в
`api/services/brand_watch.py` (`brand_watch_profiles` ≤ 20,
`brand_watch_candidates` ≤ 5000, `brand_watch_http_per_day` ≤ 200 имён в
заданиях `http_allowed`). В `tenant_quotas` колонок для этого нет.

Префикс API: `/api/brand-watch`. Чтение — роль viewer и выше. Создание и
одобрение — право `brand_watch.write`. Решение по кандидату —
`brand_watch.disposition`.

## Профиль

`POST /api/brand-watch/profiles`:

```json
{
  "name": "Acme",
  "official_domains": ["acme.example"],
  "brand_strings": ["acmebank"],
  "whitelist": [],
  "our_brand": false
}
```

Строка бренда короче четырёх символов или из общего списка (`bank`, `pay`,
`login`, …) отклоняется: она совпадёт с половиной сети. Хотя бы один
официальный домен обязателен. Белый список и официальные домены в кандидаты
не попадают.

Кнопка «Составить список» вызывает `POST /api/brand-watch/preview` и показывает имена по тем же правилам, что ночная пересборка: пропуск буквы, перестановка, похожие символы, другие окончания и фиксированные слова `login`, `secure`, `support`, `pay`, `account`, `sso`, `update`. Список можно править. Сохранение с непустым `watched_names` записывает именно его и ставит `reference.names_edited`, после чего ночная пересборка этот список не заменяет.

Создание само по себе ничего не сканирует. Одобрение — отдельный шаг:

`POST /api/brand-watch/profiles/{id}/approve` с телом `{"our_brand": true}`
или `false`.

Пока профиль не одобрен или `our_brand` ложен, каждое задание будет
`dns_only`. HTTP разрешён только когда профиль одобрен **и** отмечен как наш
бренд. Решение по кандидату (`false_positive`, `whitelisted`, `confirmed`,
`open`) само не подтверждает бренд и не запускает изъятие имени.

## Пересборка и суточный цикл

Кандидаты появляются после пересборки, не в момент создания профиля.
Диспетчер раз в сутки берёт профили, которым пора, пересобирает кандидатов и
кладёт задание в `brand_watch_jobs`. Отдельной очереди нет: это не очередь
сканирования и не `jobs.start_scan`.

Пока пересборка не прошла, список кандидатов пуст — это нормально. Смотреть
его можно сразу, не дожидаясь строки diff:

`GET /api/brand-watch/profiles/{id}/candidates`

Решение ставится тем же путём, тоже без diff:

`POST /api/brand-watch/candidates/{id}/disposition` с телом
`{"disposition": "whitelisted"}`. Кандидат с `false_positive` или
`whitelisted` по-прежнему проверяется по DNS раз в сутки, но смену состояния
не публикует.

## Сенсор

Задание забирает сенсор, который заявил capability `brand_watch`. Без этой
capability ему ничего не отдают.

`POST /api/brand-watch/jobs/claim?agent_id=` с JWT сенсора. `204` — в очереди
пусто. Тело ответа: `id`, `mode` (`dns_only` или `http_allowed`),
`payload.names`.

Сенсор выполняет задание и сдаёт наблюдения:

`POST /api/brand-watch/jobs/{id}/result` с телом `{"observations": [...]}`.
Сдать результат может только текущий владелец аренды, и только пока аренда
жива и задание в статусе `claimed`. Повтор того же `id` ничего не меняет и
второе уведомление не шлёт.

DNS-строки строит `scanner.brand_watch.observe.observe_dns`. HTTP-строки —
`scanner.brand_watch.http_observe.observe_http`, и только если режим задания
`http_allowed`, а DNS только что показал, что имя резолвится в публичный
адрес. Имя не сканируется. В область сканирования оно не добавляется.

## Что видно на странице

Страница показывает **смену состояния**, не просмотренный домен и не текст
страницы. Уведомление — diff: прежнее состояние, новое, серьёзность и
короткие причины (`state`, `hash`, `mx`, либо токены вроде `password_form`).
HTML, сертификат и тело страницы в него не входят.

`GET /api/brand-watch/diff?since=` — те же переходы для консоли.

Доставка наружу идёт в уже существующие подписки вебхуков, которые **явно**
просили вид `brand_watch.diff`. Подписка с пустым списком видов по-прежнему
означает «все события активов» и этот вид не получает. Подписка на
`new_cve` тоже не получает. Вид не публикуется как событие актива и не
добавляется в `asset_events.EVENT_KINDS`.

Сбой постановки в очередь вебхуков пишется в лог и не отменяет уже принятый
результат: наблюдение применено, страница его показывает, доставка
доживёт до следующей попытки оператора или до следующего изменения.
