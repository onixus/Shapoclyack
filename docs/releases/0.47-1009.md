# Shapoclyack 0.47-1009 — release preparation

Proposed tag: `shapoclyack-0.47-1009`. Previous published release:
`shapoclyack-0.46-0922`. This document prepares the release; it does not establish
that images, a sensor bundle or a GitHub release have been published.

## Release notes

This release brings installation-aware endpoint inventory, stronger identity and
update boundaries, expanded scanner evidence and a more complete remediation
loop. Full changes are in [CHANGELOG.md](../../CHANGELOG.md#047-1009--2026-10-09).

- Endpoint inventory accepts schemas v1/v2 for a mixed fleet. Complete source
  collections govern removal; degraded collections preserve the effective
  baseline. Native Lariska updates require signed manifests, negotiated client
  capabilities and a matching installer variant. Unsigned legacy executable
  uploads, offers and downloads are disabled.
- Sensors support API client certificates and signed native update bundles.
  Issuer-scoped signed CRLs can extend revocation to ingress or the direct TLS
  listener. Operators must configure refresh, CA chains and session handling.
- Vulnerability verification requires evidence that each detector checked the
  original endpoint. An unreachable endpoint is explicitly not machine-verified;
  unknown or multiple observing vantages do not become a verified closure.
- Web fingerprinting uses a bounded technology catalogue, including product
  versions and exposed consoles. TLS posture evaluates trust, certificate
  validity and cryptographic strength. Subdomain takeover confirmation and
  distribution-aware product matching expose incomplete evidence explicitly.
- Tenant controls include shared rate limits, custom roles, authority-based MFA
  and step-up, IdP membership synchronization, SCIM, scan priority and queue
  limits. Queued scans recheck maintenance windows when execution starts.
- Caller-owned bulk idempotency is enforced without unowned replay. Local and
  sensor runs share durable publication and projection. Compliance catalogues,
  signed evidence and CMDB/AD file import extend reporting and asset context.
- Image publication signs digests and SLSA provenance and includes SPDX SBOMs.
  Pulse remains pinned to `v1.1.0`; production images remove pip and ensurepip.
  Operator guides and installer workflows have been reconciled with the source.

## Upgrade from 0.46-0922

1. Back up PostgreSQL and the artifact store, preserve deployment configuration,
   CA/release trust anchors and revocation records. Record the old image digests.
2. Review [Operations](../operations.md) and the complete changelog. This release
   advances the database from `0059` through `0083` (there is no `0075`). Run
   `alembic -c api/db/alembic.ini upgrade head` with the new release's tooling.
   Migration `0082` refuses live unowned idempotency rows: stop any pre-`0055`
   writers and allow their 24-hour retry window to expire. Never delete live
   records to force migration. Releases 0.45/0.46 already supply the actor.
3. Drain older replicas' claim traffic and local waiters before relying on the
   maintenance-start gate. Review MFA policy: permission-derived requirements
   can confine unenrolled administrators to the Security page until enrollment.
4. Migrate legacy Lariska installations administratively to signed native
   packages, provision trusted update keys and retain identity/spool and rollback
   floors. Inventory compatibility does not restore unsigned managed updates.
5. Roll out API and scanning sensors using verified `tag@sha256:…` references.
   Lariska client-certificate acceptance remains #514; keep mTLS optional for a
   fleet that cannot present client certificates. CRL enforcement is opt-in and
   needs the [CRL runbook](../operations.md#tls-revocation-with-a-signed-crl-515).
6. Check API health, authentication/MFA, sensor registration/claim/results,
   endpoint inventory and a scoped scan. Confirm degraded inventory cannot close
   software findings and verification cannot turn missing evidence into closure.

Rollback needs a tested database plan, not only an old container image. Preserve
revocation and idempotency state; follow migration-specific rollback limits in
Operations. Do not deploy older unsigned-update behavior as a routine fallback.

## Publication handoff

- Merge the release preparation PR and freeze its resulting `main` SHA. Complete
  the full main pipeline, including both Python versions, web, SAST, manifest,
  image, smoke/E2E, Trivy/SBOM and main-only load/legacy-Nmap checks.
- Confirm the proposed git tag and all five image tags are new. A registry
  permission/network error is not proof of absence: require `MANIFEST_UNKNOWN`
  for the image-tag checks specified by [Release contract](../release-contract.md).
- Create the tag on the verified commit. Run `shapoclyack-publish` with
  `TAG=shapoclyack-0.47-1009`, `DRY_RUN=true`, `MULTIARCH=true`, `ONLY=` first.
  Complete signing-key, Pulse-access and bundle validation before a real publish.
- Publish the scanner, scanner-nmap, API, aio and aio-nmap images with the same
  tag, their signatures/provenance/SBOM and signed sensor bundle. Verify both
  architectures and record each digest. Verify the Pulse binary against the
  release's pin file; do not substitute an unpinned version.
- Publish the GitHub release with these release notes and verified assets.
  Update Kubernetes digest pins and the documented published-release baseline
  only after successful publication. A stable publish moves `latest`.
