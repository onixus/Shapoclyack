## Changes since 0.46

- Identity and fleet trust: refresh-token sessions, WebAuthn, tenant-defined
  roles, tenant-aware MFA and step-up, IdP-authoritative OIDC/SCIM, sensor mTLS
  and signed native sensor updates. Issuer-scoped signed CRLs can enforce TLS
  revocation when publication, refresh and session handling are configured.
- Scan reliability: queue priority and tenant limits, maintenance-window checks
  at execution, durable local publication, replay-safe projections and
  caller-owned bulk idempotency.
- Findings: a structured web fingerprint catalogue and exposed-console
  classification, stronger TLS certificate checks with explicit coverage,
  detector-aware mechanical verification and distribution-aware CVE matching.
- Endpoint integration: inventory schemas v1/v2, installation identities and
  collection coverage; signed native Lariska releases, capability negotiation,
  separate DEB/RPM variants and rejection of unsigned legacy updates.
- Operations: tenant lifecycle and retention, request limits, backup/restore
  procedures, signed container images and SLSA provenance, and refreshed HTTPS
  quick-start and remediation guides.

The complete change list is in [CHANGELOG.md](../../CHANGELOG.md). Lariska is
released separately; these notes describe the platform's protocol support and
do not claim that every installed endpoint Agent implements it.

## Before upgrading a validation environment

1. Back up PostgreSQL and the applicable artifact/ClickHouse stores; confirm a
   restore path before migrating. Follow
   [Upgrade and rollback](../operations.md#upgrade-and-rollback), including its
   migration-specific downgrade losses. An image rollback is not permission to
   run a blanket database downgrade.
2. For migration `0082`, stop pre-`0055` idempotency writers and wait out their
   24-hour retry window. Live unowned reservations/reports block the migration;
   expired unowned rows are removed. The published `0.46-0922` already writes
   `actor` and remains compatible with this contract. See
   [Idempotency records](../operations.md#idempotency-records-346).
3. Review the expanded tenant MFA policy and enrol affected administrators.
   Audit existing endpoint release uploads/deletes after the last old replica
   is drained. Previously stored unsigned endpoint builds are refused for
   delivery: publish signed native replacements and verify endpoint capability
   reports. See [Operations](../operations.md).
4. Drain old replicas' scan-claim traffic and local waiters before relying on
   the new maintenance-window gate. Exercise mixed-version behaviour before
   continuing the rollout.
5. Deploy all candidate components explicitly by their verified
   `tag@sha256:digest`. Repository deployment defaults and sensor installer pins
   still name the published 0.46 images; obtain candidate digests after building
   and override them in the validation environment.

### Signing key and sensor bundle

The DER SHA-256 fingerprint of the repository's `cosign.pub` is:

```text
f8d2cfa4bc0921b3f95c6cd176f9de900e63a562329383e83841a4ce8e0dae1c
```

Recompute it from the final tag (`openssl pkey -pubin -in cosign.pub -outform
DER | sha256sum`) and compare before publishing.

The publish job intentionally leaves the prerelease sensor bundle **unsigned**.
Native sensors refuse it; do not serve it as a fleet-wide auto-update. A manual
signed test bundle must be confined to a validation sensor as described in
[Sensor bundle updates](../operations.md#sensor-bundle-updates). Candidate
container images still require the normal release signatures.
