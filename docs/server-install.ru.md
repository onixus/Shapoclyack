# Установка на Linux-сервер без сборки

Самостоятельный установщик `scripts/install-server.py` разворачивает готовый
релизный all-in-one образ (API, UI, сканер) и PostgreSQL через Docker Compose.
Git, исходники проекта, компиляторы, Node.js, Go и доступ к приватному GenDec на
сервере не нужны. Сам установщик использует только стандартную библиотеку Python.

Это профиль для одного сервера: локальное выполнение сканов, постоянные Docker
volumes, без HA. NATS и ClickHouse отключены, как в базовом Kubernetes-профиле;
распределённые сенсоры через NATS и аналитика ClickHouse требуют отдельного
развёртывания по [руководству Kubernetes](../k8s/README.md).

## Требования

- Linux amd64/arm64, Docker Engine и Compose v2 с поддержкой `up --wait`;
- Python 3.9 или новее;
- минимум 4 ГБ свободной RAM, место под образы, БД, результаты и резервные копии;
- доступ к GHCR и Docker Hub, настроенный HTTPS reverse proxy на этом сервере.

Docker должен быть установлен заранее. Установщик не меняет настройки ОС,
firewall и Docker. Если GHCR требует авторизацию, предварительно выполните
`docker login ghcr.io` с правом чтения пакета. Сборка на сервере не используется
даже при отсутствии образа в реестре: установка завершится ошибкой скачивания.

## Установка

Скопируйте **один файл** `scripts/install-server.py` из проверенной версии проекта
на сервер, например:

```bash
scp scripts/install-server.py user@server:/tmp/install-server.py
```

На сервере:

```bash
sudo install -m 0755 /tmp/install-server.py /usr/local/bin/shapoclyack-server
sudo shapoclyack-server install --url https://scan.example.com
```

По умолчанию создаётся `/opt/shapoclyack`; можно выбрать `--directory /srv/shapoclyack`.
Эту же опцию затем указывайте в командах управления. Режим `prepare` вместо
`install` только создаёт файлы, не требует Docker и ничего не запускает.

Установщик:

1. Создаёт закрытый каталог, `compose.json` и `access.json` с правами `0600`.
2. Генерирует пароль администратора, PostgreSQL, JWT и master key шифрования.
3. Скачивает готовые образы; приложение закреплено по SHA-256 из манифеста релиза.
4. Ожидает PostgreSQL, останавливает API, сохраняет дамп и выполняет миграции.
5. Запускает API и ждёт успешного `/readyz`. При ошибке возвращает ненулевой код.

После успеха прочитайте `sudo cat /opt/shapoclyack/access.json`, войдите как
`admin` и смените пароль. Затем утвердите область сканирования для тенанта
в **Tenants → Scan scope**. Демоаккаунты не создаются, `OCTO_ENV=prod`.

Пароль в `access.json` — начальный; смена пароля в UI не обновляет этот файл.
`OCTO_API_USERS` в `compose.json` используется только для первоначального
заполнения пустой БД. После успешного входа его можно удалить из environment,
а `access.json` удалить. JWT и `OCTO_MASTER_KEY` сохраняйте: их потеря приведёт
к потере сессий и возможности расшифровать сохранённые секреты соответственно.

## HTTPS

API слушает **127.0.0.1:8080**, PostgreSQL не публикует порт на хосте.
TLS завершает ваш reverse proxy. `--url` задаёт внешний HTTPS origin для
CORS и адресов endpoint-агентов; сертификат эта опция не выпускает.
Для nginx в существующем TLS `server`:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 300s;
    client_max_body_size 100m;
}
```

Proxy должен работать на хосте (в контейнере `127.0.0.1` означает сам proxy).
Внешние проверки: откройте UI по указанному HTTPS URL и запросите `/readyz`.
Установщик проверяет внутреннюю готовность приложения; внешний DNS/TLS/proxy
не входят в эту проверку. Порт можно выбрать через `--port` при установке.

## Управление и данные

```bash
sudo shapoclyack-server status
sudo shapoclyack-server logs
sudo shapoclyack-server backup
sudo shapoclyack-server stop
sudo shapoclyack-server start
```

`stop` сохраняет контейнеры и тома; Docker поднимает сервисы после перезагрузки
по `restart: unless-stopped`, если они не были явно остановлены.
`start` повторно скачивает образы, делает дамп перед миграциями и проверяет
готовность. Не используйте его как проверку статуса: он останавливает API.
При неудачной первоначальной установке исправьте причину и выполните `start`;
повторный `install` намеренно отказывается перезаписывать каталог.

Тома `postgres`, `output`, `state`, `config`, `inputs` получают уникальный
префикс проекта из `compose.json`. Каталог установки хранит конфигурацию и
секреты, сами данные находятся в Docker volumes. Не меняйте поле `name`,
не выполняйте `down -v` и не удаляйте volumes при обновлении.
Ротация логов ограничена тремя файлами по 10 МБ на контейнер.

`backup` создаёт PostgreSQL custom-format dump в `backups/`. Это **не полный
backup**: отдельно сохраняйте `compose.json` (содержит ключи), результаты,
состояние и конфигурацию из volumes. Для согласованной копии остановите API,
сделайте дамп и снимки томов. Переносите копии за пределы сервера; установщик
не удаляет старые дампы автоматически.

## Обновление и восстановление

Для другой версии при первой установке передайте
`--image ghcr.io/onixus/shapoclyack-aio:<tag>@sha256:<digest>`.
Дайджест должен относиться к нужному релизу и архитектуре; `latest` не принимается.

Перед обновлением существующей установки сделайте полную резервную копию.
Сохраните старый `compose.json`, замените **только** `services.api.image` на
проверенный `tag@sha256` нового релиза и выполните `start`. Параметр `--image`
используется только при `prepare/install`, существующие файлы он не меняет.
Том `config` сохраняет конфигурацию предыдущей версии: изменения её формата
следует переносить согласно release notes, а не удалять том вслепую.

При ошибке миграции API остаётся остановленным, дамп перед попыткой лежит
в `backups/`. Исправьте причину и повторите `start`. Откат образа сам по себе
не откатывает схему БД: для восстановления используйте старую конфигурацию,
соответствующий дамп через `pg_restore` и согласованные копии томов на отдельной
установке. Не запускайте старый API поверх уже обновлённой схемы без проверки
совместимости.
