# Архитектурный разбор — 18 сентября 2026

Проверенный срез: `main`, `b12df58` (релиз приложения `0.45-0916`).
Локальная ветка актуализирована с `b4ff5eb` через fast-forward после

До актуализации рабочее дерево было чистым.

Это разбор исходного кода и локальных проверок, а не аудит работающего кластера.
Ниже разделены подтверждённые свойства реализации и сценарии отказа, которые
ещё нужно воспроизвести на PostgreSQL и нескольких репликах.

## Архитектура и её сильные стороны

Система представляет собой модульный монолит control plane с отдельно
исполняемыми сенсорами и несколькими специализированными хранилищами.
Такое разделение подходит текущим задачам; приоритет — укрепить завершение
заданий и границы фоновой работы, прежде чем выделять новые микросервисы.

| Слой | Реализация и ответственность |
|---|---|
| UI | `web-next/`: Next.js static export, React Query, tenant-контекст; статику обслуживает API |
| Control plane | `api/routes/`, `api/services/`: авторизация, задания, inventory, vulnerability lifecycle, отчёты и интеграции |
| Транзакционные данные | PostgreSQL, SQLAlchemy, Alembic; SQLite — отдельный путь для разработки |
| Исполнение | `agent/worker.py` — сенсор; `scanner/pipeline/` — этапы сканирования; `recon/` — Go-компонент |
| Endpoint inventory | Внешний Lariska Agent отправляет снимки; не является Python-сенсором и не забирает scan jobs |
| Асинхронный обмен | NATS JetStream: предложения заданий, ingest и события; состояние заданий хранится в PostgreSQL |
| Результаты | Файлы/PVC или S3 для артефактов; ClickHouse для аналитической проекции |

Подробный поток данных: [Architecture](architecture.md). Существенные уже
реализованные механизмы:

- Состояния заданий централизованы в `api/services/job_states.py`; есть leases,
  retry, idempotency keys и проверка claim attempt при входе в completion.
- PostgreSQL row locks разделяют работу реплик; advisory locks ограничивают
  dispatchers. Распределённая координация не сводится к памяти процесса.
- Tenant-проверки находятся на сервере; сенсоры и endpoint Agents различаются
  по `agent_kind`. UI не является границей авторизации.
- Webhook fan-out отделён от HTTP-доставки; очередь, история и DLQ находятся
  в PostgreSQL. Есть ограничения SSRF и подписывание payload.
- PostgreSQL использует Alembic, а не автоматическое создание схемы при старте.
- Есть отдельные liveness/readiness, метрики, thin API image и профиль `prod-ha`.

## Приоритетные выводы

### P1 — синхронный ingest блокирует event loop API

**Подтверждено кодом.** В [api/routes/agents.py](../api/routes/agents.py)
`async def upload_results` после чтения файла напрямую вызывает синхронный
`jobs_service.complete_job`. В [api/services/jobs.py](../api/services/jobs.py)
этот вызов выполняет SQL, публикацию в NATS, распаковку, запись артефактов
и обновление проекций. Для S3 путь включает синхронный сетевой I/O.

Медленная загрузка результатов задерживает обработку других запросов тем же
ASGI event loop, включая heartbeat и probes. Число реплик уменьшает область
влияния, но не исправляет поведение отдельной реплики. Размер фактической
задержки в этом разборе не измерялся.

**Действие:** вынести синхронную обработку из event loop с ограничением числа
одновременных ingest. Следующий шаг — durable ingest worker с отдельным
состоянием приёма. Не запускать неограниченное число фоновых потоков.

**Критерий проверки:** искусственно задержать artifact store при upload и
одновременно измерить heartbeat/readyz; они должны оставаться отзывчивыми,
а очередь ingest и память — ограниченными.

### P1 — fencing проверяется до длительной обработки, а не при финальной записи

**Подтверждено кодом; конкурентный сценарий требует воспроизведения.**
`complete_job` проверяет `assigned_agent_id` и `attempt` под row lock, затем
закрывает транзакцию и обрабатывает архив. Завершающий `_update_job` снова
блокирует строку и проверяет допустимость перехода, но не сверяет исходные
`attempt` и владельца. `reap_expired_leases` может между этими операциями
переотдать задание. В [agent/worker.py](../agent/worker.py) контекст
`_busy_heartbeats` заканчивается до `client.upload_results`.

Если ingest длится дольше оставшейся lease и новая попытка уже получила
задание, старая обработка потенциально может завершить новую попытку:
`claimed/running → succeeded` остаётся допустимым переходом. Побочные эффекты
в артефактах и проекциях происходят ещё до финальной записи статуса.

**Действие:** ввести отдельную lease на ingest; финальную запись выполнять
условно по `(job_id, attempt, owner, ingest token)`. Артефакты сначала писать
в staging, привязанный к попытке, и только затем публиковать принятый результат.
На период передачи и обработки результата нужен явно определённый heartbeat.

**Критерий проверки:** на PostgreSQL остановить первую completion после
первой транзакции, истечь lease, выдать вторую попытку, продолжить первую.
Она не должна менять outcome или опубликованные артефакты второй попытки.

### P1 — успешное задание не гарантирует актуальность всех проекций

**Подтверждённый компромисс реализации.** `complete_job` последовательно
публикует raw results, сохраняет артефакты, обновляет assets/vulnerabilities,
публикует события и завершает job. Общей транзакции между этими действиями нет.
`_track_vulnerabilities_best_effort` и `_publish_asset_events_best_effort`
протоколируют ошибку, но позволяют завершить scan успешно; asset upsert
дополнительно сохраняет ошибку на job. Это согласуется с текущей документацией.

Артефакты могут присутствовать, а lifecycle и уведомления — отставать.
Идемпотентный повтор уже завершённого upload возвращает сохранённый outcome
и не повторяет эти действия. Следующее сканирование не является гарантией
восстановления пропущенного события предыдущего запуска.

**Действие:** хранить durable задания обновления проекций и отправки событий,
их версии, попытки и ошибки. Использовать transactional outbox там, где событие
следует из PostgreSQL-коммита; для S3/NATS добавить reconciler и повторяемые
операции. Не пытаться объединить все хранилища одной SQL-транзакцией.

**Критерий проверки:** при отказе каждого хранилища и перезапуске API
неполная обработка видима оператору и автоматически доводится до конца без
повторного сканирования и повторных lifecycle-событий.

### P2 — NATS расширяет область отказа на весь HTTP control plane

**Подтверждено реализацией и существующим тестом.** В
[api/services/health.py](../api/services/health.py) `BLOCKING_CHECKS` включает
PostgreSQL и NATS. При настроенном, но недоступном NATS все API-реплики
могут потерять readiness одновременно. ClickHouse и S3 лишь переводят health
в degraded. Политика NATS закреплена в `test_nats_still_blocks_readiness`
из [tests/test_api_probes.py](../tests/test_api_probes.py).

При этом предложение задания имеет HTTP claim fallback, а часть CRUD не
требует брокера. При отказе публикации `publish_raw_results` возвращает `published=false`,
а `complete_job` не проверяет этот флаг: upload может завершиться, хотя
сообщение для аналитики не доставлено.

**Действие:** сначала описать capability matrix при отказе NATS, затем решить,
нужна ли общая блокировка readiness или отдельный статус dispatch/ingest.
Ослабление readiness должно сопровождаться восстановлением пропущенных
публикаций, иначе доступность HTTP скрывает отставание аналитики.

### P2 — фоновые задачи масштабируются вместе с HTTP-репликами

[api/app.py](../api/app.py), `lifespan`, запускает scheduler, retention,
software matching, reports, SLA, reaper, webhooks и ticket sync в API-процессе.
Часть задач координируется locks, однако ресурсы и жизненный цикл они делят
с HTTP. `jobs.py` содержит 2810 строк, `schemas.py` — 2997,
`web-next/src/lib/api.ts` — 3962: это точки концентрации изменений, а не
самостоятельное доказательство дефекта.

**Действие:** добавить явные роли процессов и наблюдаемость workers, сохраняя
общие доменные сервисы; разбить job orchestration по операциям claim/lease,
completion и execution. Контракт API/TypeScript проверять автоматически.
Приоритет отделения workers определяется нагрузкой, а не количеством файлов.

### P2 — фактические проверки отличаются от описанных

[tests/conftest.py](../tests/conftest.py) пропускает PostgreSQL-dependent
наборы без URL тестовой БД. До этой актуализации development guide перечислял
только NATS и SSH как инфраструктурные условия пропуска. Зелёный локальный
pytest поэтому не доказывает tenant isolation или корректность row locks.

Есть и дрейф CI: Jenkins и requirements-dev фиксируют Ruff `0.15.22`, reference
GitHub workflow — `0.15.20`; оба CI lint-вызова проверяют `scanner api tests`,
не включая `agent`. Формулировка guide о совпадающих stage lists слишком
сильная: в Jenkins есть Semgrep-стадия, не представленная в reference workflow.

**Действие:** синхронизировать reference workflow и вынести общие проверки
в скрипты; проверять sensor package lint-ом; интеграционный gate должен
проверять наличие ожидаемых PostgreSQL/NATS-наборов, а не только exit code.
В этой актуализации исправлена документация; CI pipeline не менялся.

## Эксплуатационные границы

`prod` и `prod-ha` не взаимозаменяемы. `prod-ha` требует внешнего PostgreSQL,
общего RWX или S3, настройки NATS и замены placeholders. ClickHouse остаётся
однорепличным; профиль сам по себе не доказывает HA всех данных. Проверка
Kustomize доказывает рендеринг, но не готовность к применению, recovery или SLO.
Источник требований: [High availability](high-availability.md).

Следующая полезная проверка — изолированный стенд с PostgreSQL, NATS, S3,
двумя API-репликами и сенсором: конкурентный completion, отказ брокера,
перезапуск во время ingest и восстановление проекций. После этого — отдельные
измерения latency и backup/restore drill.
